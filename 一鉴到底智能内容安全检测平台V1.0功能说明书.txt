一、软件概述


【1.1 产品定位】

一鉴到底（YiJianDaoDi）是一款基于人工智能的Agent行为安全平台。系统采用"四Agent串行检测+行为基线建模"双核架构，集成DeepSeek大语言模型能力，不仅提供文本、图片、代码、论文、简历、合同、营销文案、视频等8大场景的专业化内容安全检测服务，更实现了Agent行为监控、行为基线建模、异常行为检测等深度安全能力，从"内容检测"扩展到"行为检测"，全方位保障AI Agent系统的安全性。

【1.2 核心价值】

  多维检测：单一请求触发4个专业AI Agent串行分析，覆盖审核、核查、取
    证、裁决四个维度
  实时反馈：基于SSE（Server-Sent Events）流式推送技术，每个Agent完
    成分析后即时向用户端推送进度和结果
  分布式算力：P2P分布式计算网络，支持节点发现、任务调度、结果聚合，
    充分利用闲置算力资源
  技能生态：200+业务技能矩阵，支持按场景、层级、变现模式灵活配置

【功能1.2】四Agent串行检测引擎

  功能描述：
    用户提交检测请求后，系统按固定顺序依次调度4个专业AI Agent进行串行
    分析，每个Agent接收前序Agent的分析结果作为上下文，形成链式推理。

  Agent序列：

    ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
    │ 内容审核员 │ → │ 事实核查官 │ → │ 数字取证员 │ → │  裁决官   │
    │ Auditor   │   │ Verifier │   │ Archiver  │   │  Judge   │
    └──────────┘   └──────────┘   └──────────┘   └──────────┘
       深度1           深度2          深度3          深度4

  各Agent职责：

    (1) 内容审核员（Auditor）
        敏感词检测与合规性审查
        AI生成内容痕迹识别（AI概率评估）
        内容分类与置信度判定
        输出：level(等级), summary(摘要), details(12条检测详情)

    (2) 事实核查官（Verifier）
        基于审核员输出进行二次验证
        逻辑一致性检查
        引用来源真实性核验
        输出：独立分析报告 + 置信度修正值

    (3) 数字取证员（Archiver）
        元数据分析（如图片EXIF、代码哈希）
        模式识别与异常标记
        证据链固化准备
        输出：取证报告 + 证据索引

    (4) 裁决官（Judge）
        综合前三Agent结果进行最终裁决
        dangerCount>=2 → danger（高风险警报）
        dangerCount>=1 → warning（存在风险提示）
        else → safe（安全通过）
        输出：finalLevel, finalSummary, recommendations(改进建议)

  技术实现：
    后端接口：POST /api/agent/public/detect/
    运行时引擎：OpenRath RathRuntime.run_detect_pipeline()
    DeepSeek API调用：每个Agent通过OpenRath Agent.forward()统一调用
    链式上下文传递：SequentialWorkflow自动将前序Agent结果注入下一Agent
    Session管理：每个Agent输出独立Session（Fork），注册到SessionGraph
    强制JSON格式解析：正则提取JSON块，容错降级
    会话持久化：每次检测创建Django AgentSession + OpenRath Session双写

【功能1.3】SSE流式实时推送

  功能描述：
    检测过程中，后端通过Server-Sent Events协议逐个Agent向前端推送执行进度，
    用户无需等待全部完成即可看到中间结果。

  事件流格式：

    event: start       → {"type":"start","message":"开始检测"}
    event: agent_start → {"type":"agent_start","index":0,"name":"auditor"}
    event: agent_complete → {"type":"agent_complete","index":0,"result":{...}}
    event: agent_start → {"type":"agent_start","index":1,"name":"verifier"}
    event: agent_complete → {"type":"agent_complete","index":1,"result":{...}}
    ...（依次类推4个Agent）...
    event: complete    → {"type":"complete","finalResult":{...}}

  技术实现：
    - 运行时引擎：OpenRath RathRuntime（收集全部Agent结果后按SSE格式推送）
    - 后端：Django StreamingHttpResponse + SSE text/event-stream格式
    - 接口：POST /api/agent/public/detect-stream/
    - 前端：fetch API + ReadableStream逐行解析AsyncGenerator
    - Vite代理配置：对/detect-stream/路径禁用缓冲（buffer:false）
    - complete事件包含 graphInfo 字段（SessionGraph血缘信息）

【功能1.5】上下文智能管理

  功能描述：
    对话过程中自动管理上下文窗口长度，防止超长对话导致API调用失败或成本
    过高。采用三级防护机制确保稳定性。

  管理策略：

    第一层 — 硬截断：
      MAX_TOTAL_TURNS = 20（最大20轮对话，超出强制丢弃最早轮次）

    第二层 — 智能压缩：
      - 触发条件：连续8轮对话或累计Token超过4000
      - 压缩方式：保留最近3轮完整对话，更早轮次摘要为一段总结文本
      - 重试机制：压缩失败最多重试1次，失败则使用fallbackCompress兜底

    第三层 — Token上限保护：
      buildMessagesForApi() 构建最终prompt时校验总Token不超过8000

  配置参数：
    MAX_TURNS_BEFORE_COMPRESS = 8     （压缩前最大轮次）
    COMPRESSION_THRESHOLD_TOKENS = 4000  （压缩触发Token阈值）
    MAX_CONTEXT_TOKENS = 8000          （上下文硬上限）
    KEEP_RECENT_TURNS = 3              （压缩保留最近轮次）
    MAX_COMPRESS_RETRIES = 1            （压缩重试次数）

【功能1.6】OpenRath多智能体运行时集成  （F-AI-11）

  功能描述：
    系统集成了 OpenRath v1.2.1 多智能体运行时框架（BSD-3-Clause开源协议），
    采用"Session 为一等公民"的核心设计理念重构了四Agent串行检测引擎。
    所有Agent协作状态通过 Session 对象显式传递，支持动态 Session Graph 做路由
    和完整复现。

  OpenRath 核心概念映射：

    PyTorch 概念              OpenRath 对等物              本项目应用
    ──────────────────────────────────────────────────────────────
    Tensor(携带数据)     →   Session(携带Agent状态)   →   每次检测创建Session
    device(控制放置)     →   Backend(执行后端)        →   Local/Process沙箱
    Parameter(持久化)    →   Memory(记忆存储)         →   本地记忆后端
    Module(组合计算)     →   Workflow/Agent(编排行为)  →   SequentialWorkflow

  集成架构：
    用户输入 → RathRuntime.create_session() → Session(一等公民)
             → SequentialWorkflow([auditor, verifier, archiver, judge])
             → 每个Agent输出新Session(Fork+血缘注册)
             → SessionGraph 记录完整血缘图
             → Django AgentSession/AgentMessage 持久化

  技术实现：
    适配层文件：backend/auth_app/openrath_adapter.py（约900行）
    实现的OpenRath核心模块：
      - Session / ChunkTable：一等公民运行时状态
      - Agent：智能体定义（system_prompt, provider, tools, memory）
      - Workflow：工作流编排（SequentialWorkflow串行/ParallelWorkflow并行）
      - BackendSandbox：可插拔沙箱后端（LocalSandbox/ProcessSandbox）
      - MemoryStore：可插拔记忆后端（LocalMemoryStore关键词匹配）
      - FlowToolCall：工具调用接口（JSON Schema + Python callable）
      - Compressor：上下文压缩器
      - SessionGraph：动态Session Graph管理器（路由与复现）
      - RathRuntime：统一运行时入口
    工厂函数：create_quad_agent_runtime() 一键获得完整多智能体运行时
    兼容性说明：因当前Python 3.14超出OpenRath官方支持范围(<3.14)，
                 采用兼容适配层方案实现，API完全对齐，未来可无缝替换为官方库。

  开源信息：
    GitHub: https://github.com/Rath-Team/OpenRath
    官网: https://www.openrath.com/
    文档: https://docs.openrath.com/
    PyPI: https://pypi.org/project/openrath/
    协议: BSD-3-Clause
    版本: v1.2.1

【功能1.7】Session Graph血缘追踪  （F-AI-12）

  功能描述：
    基于 OpenRath 的 Session Graph 机制，每次检测的所有 Session（根Session +
    4个Agent各自输出的Fork Session）自动注册到血缘图中。支持：
      - 查询完整执行链路（从根Session到最终结果）
      - 查看每个Session的分支（Fork）关系
      - 复现完整的执行路径（用于调试和审计）

  血缘数据结构：
    每个Session记录：
      - session_id: UUID唯一标识
      - kind: 血缘类型(root/fork/agent_run/merge/compress)
      - operator: 操作名称（如 "agent:auditor"）
      - parents: 父Session ID列表
      - children: 子Session ID列表
      - chunk_count: 消息数量
      - usage: Token用量统计

  API接口：
    detect-stream 返回的 complete 事件中包含 graphInfo 字段：
      - rootSessionId: 根会话ID
      - lineage: 完整血缘链路
      - stats: 图统计信息
      - replayUrl: 复现接口路径

【功能1.8】动态路由与复现  （F-AI-13）

  功能描述：
    利用 OpenRath Session Graph 的路由能力，系统可以：
      - 动态决定下一个Agent应该接收哪些Session作为输入
      - 在Agent执行失败时自动路由到备用分支
      - 支持完整复现任意历史检测的执行过程
      - 导出 Session 为 JSONL 格式用于离线分析

  复现流程：
    1. 从 complete 事件的 graphInfo 中获取 rootSessionId
    2. 调用 SessionGraph.replay(session_id) 获取完整执行路径
    3. 按 lineage 顺序重放每个步骤的输入输出
    4. 输出 replayable 标识判断是否可完整复现

【功能7.1】节点发现服务（Node Discovery）

  功能描述：
    P2P网络中的节点注册与发现机制，维护全网可用计算节点的实时拓扑。

  核心能力：

    心跳保活：定期心跳（默认30s间隔），超时（90s）自动标记离线

    拓扑查询：按条件搜索节点（在线/特定能力/最低信誉分）

【功能7.2】任务调度器（Task Scheduler）

  功能描述：
    将上层下发的计算任务拆解为分片（Shard），分发到合适的P2P节点并行执行。

  调度流程：
    (1) 接收任务 → 解析DAG依赖关系
    (2) 任务拆分 → 按数据规模和复杂度拆分为N个Shard
    (3) 节点匹配 → 查询EIHM成本路由获取最优节点列表
    (4) 任务分发 → HTTP/gRPC推送到目标节点
    (5) 状态追踪 → 状态机：created→dispatched→running→success/failed/timeout
    (6) 结果回收 → 节点执行完毕回调上报结果

  状态机转换：
    created → dispatched → running → success
                          ↘ failed → retry → running (最多3次)
                          ↘ timeout → redistribute

【功能7.3】结果聚合器（Result Aggregator）

  功能描述：
    收集所有分片执行结果，进行冲突解决和有序合并。

  聚合策略：
    无冲突：直接按shard_index排序拼接
    有冲突：多数投票共识（majority vote）
    超时未返回：使用备用节点重新执行该分片
    最终输出：聚合报告 + 完整日志 + 性能指标

【功能7.4】EIHM成本路由器（Cost Router）

  功能描述：
    基于经济激励模型（Economic Incentive Hierarchy Model）的智能任务路由
    算法，为每个分片选择最优执行节点。

  评分因子（综合加权评分）：

    因子              权重    说明
    ──────────────────────────────
    算力匹配度        30%     节点CPU/内存/GPU是否满足需求
    网络延迟          25%     RTT往返时延（ping测量）
    当前负载          20%     节点当前正在执行的任务数
    信誉评分          15%     历史执行成功率/及时率
    价格报价          10%     节点申报的单位算力价格

  输出：排序后的候选节点列表（Top-N），调度器从中选择最优节点分发。

【功能7.5】沙箱执行引擎（Sandbox Executor）

  功能描述：
    在隔离的安全环境中执行用户提交的计算任务，防止恶意代码影响宿主系统。

  支持的语言运行时：

    语言      执行方式          安全措施
    ──────────────────────────────────────
    Python    Pyodide(WASM)    浏览器沙箱，完全隔离
    JavaScript Node.js子进程  资源限制(cgroups)，超时杀进程
    Bash      受限Shell        禁止rm/mkfs/dd等危险命令
    HTML      iframe sandbox   sandbox属性限制

  资源限制：
    最大内存：512MB
    最大CPU时间：60s
    最大输出大小：10MB
    网络访问：禁止（除非显式授权）

【功能8.1】ASS零信任安全网关

  功能描述：
    所有API请求经过的四重安全检查中间件，实现零信任安全模型。

  四重防线：

    第一道 — inspect（输入检测）
      SQL注入检测（正则匹配UNION/SELECT/DROP等关键字）
      XSS检测（<script>/onerror等标签和事件）
      命令注入检测（;|&$(){}等shell元字符）
      路径遍历检测（../..\..\etc/passwd模式）
      检测结果写入安全日志

    第二道 — sanitize（输入净化）
      HTML标签清理（strip_tags，保留白名单标签）
      特殊字符转义（<>&"'→HTML实体）
      JSON格式规范化（防止prototype污染）
      URL编码规范化（防双重编码攻击）

    第三道 — classify（内容分类）
      请求内容类型识别（正常/可疑/恶意）
      基于规则的快速分类（关键词匹配+模式识别）
      风险等级评定（low/medium/high/critical）
      高风险请求触发额外验证步骤

    第四道 — sign/verify（签名验签）
      请求签名生成（HMAC-SHA256，基于Timestamp+Body+Secret）
      签名验证（防重放攻击：时间窗±5分钟）
      响应签名（确保传输完整性）
      ASS签名格式：timestamp.nonce.signature

  日志记录：
    每次请求记录：[AUTH/UNAUTH] METHOD PATH | ip=xxx - 结果
    安全事件分级：INFO/WARN/ERROR/CRITICAL
    RotatingFileHandler日志轮转（按大小/日期）

【功能9.1】不可篡改审计日志

  功能描述：
    基于SHA256哈希链的审计日志存储机制，确保每条记录不可被事后篡改。

  数据结构：
    每条审计记录包含：
    {
      "index": 序号,
      "timestamp": ISO8601时间戳,
      "action": 操作类型(detect/chat/install/...),
      "actor": 操作者标识,
      "data_hash": 本条数据SHA256,
      "prev_hash": 前一条记录的hash（链式指针）,
      "signature": ASS数字签名
    }

  链式完整性验证：
    任意记录的prev_hash必须等于前一条记录的整体hash
    修改任意一条记录会导致后续所有hash不匹配
    验证函数：verify_chain_integrity() → bool
